# What the harness must make agents do

Read this before designing or changing any skill, subagent or hook. Each requirement comes from observed
agent failures in real work, not from theory.

## The agent is an engineer, not a code generator

1. **Understand the problem before the solution.** Find who needs the change and why, and whether the
   requested solution solves it. Study the domain and how comparable products solve the same problem when
   the task is new territory.
2. **Treat requirements as a draft.** Task descriptions are often written quickly or generated by AI and
   contain mistakes. Look for contradictions with current behavior, code and data, missing edge cases,
   side effects on other features, and a simpler or better approach. Say so before writing code.
3. **Ask what matters, only what matters.** Ask when different answers lead to different code. Never ask
   what the code, the docs or the data already answer. Too many questions is a failure too.
4. **Push back, with a limit.** Propose the better alternative with reasons, and stop the task when it
   risks data, security, money or legal compliance. How hard to push is a per-project setting
   (`quiet` / `balanced` / `strict`), because a task from a product manager and an owner's own idea need
   different treatment.
5. **Separate investigating from changing.** "Find out why", "check", "analyze" means answer with evidence
   and edit nothing.
6. **Facts over hypotheses.** Check code, logs or data before concluding how the system behaves. Label
   anything unverified as an assumption.

## The work fits the project

7. **Reuse first.** Find existing functions, components, services and scripts before writing new ones.
   Duplicating what exists is one of the most frequent corrections.
8. **Follow existing patterns by default.** Match the project's UI conventions, API style and data access.
   When a fresh approach is better, propose it explicitly at design time as an alternative; never swap
   patterns silently, and never copy a pattern that is known to be bad.
9. **Keep it simple.** No speculative abstractions, no workaround patches that hide the root cause, no
   unrequested refactors, no changes or `git add` outside the task's scope.
10. **Complete means everywhere.** A change lands in every form, screen, endpoint, enum and config it
    applies to. List the touch points before coding and check them before finishing.
11. **MVP quality equals product quality.** A quick prototype must be continued, not rewritten, if it
    succeeds.

## Done means verified

12. **Prove it works where it runs.** Run the tests, typecheck and the app; for UI, open the screen and look
    at a screenshot at desktop and mobile widths. "Works locally" is not enough when CI or another
    environment differs. Show evidence (command output, screenshots), not claims.
13. **Grow tests where there are none.** Many projects have no tests. Add focused tests for the changed
    behavior instead of requiring a full suite that doesn't exist.
14. **Never leak data.** No personal data, real phone numbers, secrets or production URLs in code,
    fixtures, examples or logs.

## Design

15. **Modern, considered UI, not a template.** Work from the project's design system, propose options for
    new screens before building, and verify visually. Agents produce generic designs when they can't see
    their result.

## The full cycle

One prompt should be able to take a task to a reviewed change. The stages, with human checkpoints marked:

1. Intake: task text or a tracker issue.
2. Analysis and requirements critique.
3. **Questions and alternatives → human confirms the problem statement.**
4. Spec with verifiable acceptance criteria, reuse and touch points.
5. Design and architecture; **human picks when there are options.**
6. Implementation in a fresh session from the spec.
7. Verification with evidence; independent review in a fresh context that reports, not rewrites.
8. **Merge request and tracker update → human accepts.**
9. Retro: what the human corrected becomes a harness fix.

Build the cycle from the front. The harness is used from its first increment and improved from what goes
wrong in real tasks.

## Environments

- Standalone repositories and workspaces where one folder contains several repositories, each with its own
  CLAUDE.md and skills. Subagents and hooks of nested repositories don't load from the workspace root, so
  the harness ships its roles and hooks in the plugin.
- Local interactive sessions first; background and parallel runs later. Parallel work in a non-git
  workspace needs per-repository worktrees.
- Trackers and git hosts vary (Jira, Linear, GitLab, GitHub and others); integrations are pluggable.

## Cost

Route work by role. Reading and searching runs on a cheaper model in a subagent; requirement analysis and
architecture get the strongest model; implementation and review sit in between. Short sessions per stage
beat one long session, because re-reading accumulated context dominates token spend.

| Role | Starting point |
|---|---|
| Scout: search, logs, docs | sonnet, low effort |
| Analyst, architect | strongest model, high effort |
| Implementer from a spec | opus, medium effort |
| Reviewer | not weaker than the implementer |
| Routine: tracker updates, reports | haiku or sonnet, low effort |

These are hypotheses to confirm with measurement, not fixed rules.

## Measurement

Every mechanism must earn its place. Track corrections per session from real transcripts continuously;
use benchmark and trap-task A/B runs when choosing between variants. Remove what doesn't help.
